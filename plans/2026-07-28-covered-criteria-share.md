# Covered-criteria share of real findings — measured, with the circularity flagged

**Task**: measure what share of real-world accessibility problems fall inside the 14
WCAG 2.2 A+AA criteria Beacon has any detector for (`VALIDATION.md#wcag-criterion-coverage`,
14/55 = 25.5%), using a population labelled independently of Beacon's own detectors.

## The circularity trap (stated up front, per work order)

Counting findings Beacon *emitted* and asking what share map to criteria Beacon
*covers* is circular by construction — a detector cannot emit a finding tagged with a
criterion it doesn't cover, so the answer is 100% before any data is touched. **That
number must never be published.** Every computation below uses a population that was
NOT generated by running Beacon's own detectors and reading their tags back.

## Population used, and why

`beacon/benchmark/2026-07-06-ground-truth/` (canonical, engine `@8`,
`pr-analysis-v8.json`) — the same 20-site inventory VALIDATION.md cites for the
0.727-pattern / 0.829-instance recall figures. Per its `README.md`: candidates were
drawn from **Beacon findings ∪ Lighthouse raw failure nodes ∪ an independent markup
sweep**, then every candidate was judged by two adversarial AI passes against WCAG
semantics directly on the markup — not by trusting either tool's tag. The markup-sweep
arm and the adversarial judgment are what make this independent of Beacon at the
**instance** level (Beacon's own tag on a finding was never the arbiter of whether a
violation existed).

Rejected populations:
- `beacon-benchmark-100/survey-audits/*.json` — these are Beacon's own audit output
  (`tool_version: "beacon codex static baseline"`, confirmed by reading one file
  directly). Fully circular; not used for anything here.
- Raw Lighthouse JSON exists for the wider 87/100-site benchmark
  (`beacon-benchmark-100/raw/*-lh.json`) and could give a larger-N, wider-rule-coverage
  cross-check. Not computed here: it shares the identical **same-provenance bias**
  the GT study's own `critic.md` already names ("Beacon and Lighthouse both wrap
  axe-core rulesets, so 'two of three sources agree' is often one engine counted
  twice, not independent confirmation") — widening N does not fix the independence
  problem, it only reruns the same tool-coverage bias at larger scale. Flagged as a
  possible future cross-check, not attempted.

## A second circularity the GT study's own README discloses (read carefully — this is the real finding)

The GT study's scope was **pre-selected to 10 structural classes**: image-alt,
link-name, button-name, frame-title, input-label, heading-order, list-structure,
html-lang, document-title, meta-viewport-zoom. Per its own method section: *"Contrast
and target-size excluded (no measurement independent of axe available)."* — i.e. the
class list was chosen because these are the classes an independent human/AI markup
sweep CAN verify, which is nearly the same criterion as "classes an automated tool can
check." This is not the naive trap above (candidates weren't generated only from
Beacon's output), but it is a real, milder version of it: **the population was never
capable of surfacing a real-world violation in any of the 41 WCAG A+AA criteria that
have no automatable structural proxy** (contrast reasoning beyond axe, keyboard traps,
focus order, captions, timing, error identification, etc.) — not because those
problems don't occur, but because this study never went looking for them there.

Consequence stated plainly: **any "share" computed from this population is a measure
of overlap between "independently-structural-checkable classes" and "Beacon's
detector scope," not a measure of overlap between "all real-world a11y problems" and
Beacon's detector scope.** Both circularities are disclosed below; neither is hidden
in the headline number.

## The exact computation

Source: `beacon/benchmark/2026-07-06-ground-truth/pr-analysis-v8.json`, `tools.beacon`
(the current, `@8`-and-later canonical figures — NOT the stale `@4`-era
`beacon-benchmark-100/ground-truth-2026-07-06/pr-analysis.json`, which predates the
fixes and is superseded).

```
cd beacon/benchmark/2026-07-06-ground-truth
node -e "
const pr = require('./pr-analysis-v8.json');
const b = pr.tools.beacon;
let pSum=0, iSum=0;
for (const [k,v] of Object.entries(b)) {
  if (k==='total') continue;
  pSum += v.tp+v.fn+v.oos;
  iSum += v.tp_w+v.fn_w+v.oos_w;
}
console.log('patterns', pSum, 'instances', iSum);
"
```

Cross-checked directly against `inventories.json` (the raw per-violation records,
independent of the aggregation script):

```
node -e "
const inv = require('./inventories.json');
const counts = {};
for (const site of inv) for (const v of site.violations||[]) counts[v.criterion]=(counts[v.criterion]||0)+1;
console.log(counts);
"
# → image-alt:18 link-name:23 button-name:8 heading-order:5 frame-title:2
#   list-structure:8 input-label:1 meta-viewport-zoom:1  (sums to 66, matches n_violation_patterns)
```

Every one of the 8 classes with at least one real violation maps (table above) to one
of the 5 distinct WCAG SCs {1.1.1, 1.3.1, 1.4.4, 3.3.2, 4.1.2} — all 5 already on
Beacon's 14-criterion covered list.

## Results

**Pattern-level**: 66 of 66 GT-verified violation patterns sit on a Beacon-covered
criterion → **66/66 = 100%**.

**Instance-level**: 350 of 350 GT-verified violation instances sit on a Beacon-covered
criterion → **350/350 = 100%**.

Per-class breakdown (patterns / instances / Beacon's own recall on that class, from
the same file — recall is NOT part of the coverage-share claim, shown only for
context on how weak "covered" can still be):

|---|---|---|---|---|

| link-name | 4.1.2 | 23 | 194 | 0.783 |
| button-name | 4.1.2 | 8 | 16 | 0.500 |
| frame-title | 4.1.2 | 2 | 3 | 1.000 |

## Criteria with human labels but NO Beacon detector

**None.** Zero of the 66 patterns / 350 instances land on any of the 41 WCAG A+AA
criteria Beacon has no detector for.

This is the honest gap, stated the way the work order asked for it: **this empty list
is a blind-spot artifact of the study's own scope, not evidence that no such gap
exists in the world.** The GT study was structurally incapable of finding a violation
in, say, 2.1.2 No Keyboard Trap or 4.1.3 Status Messages, because it never went
looking there — its candidate classes were fixed at 10 (all structural/DOM-checkable)
before any site was audited. Nothing here supports or refutes a claim about how
accessibility problems are distributed across the other 41 criteria in the real
world.

## Limits (read before citing any number above)

1. **Naive circularity, avoided**: candidates came from Beacon ∪ Lighthouse ∪ an
   independent markup sweep, adversarially re-judged against WCAG semantics on the raw
   markup — not from reading Beacon's own tags back.
2. **Scope circularity, not avoided and not avoidable with this dataset**: the GT
   study's 10-class scope was chosen because those classes are checkable independently
   of axe — a criterion nearly identical to "automatable." Every criterion this study
   could ever have found a violation in was already inside Beacon's automatable
   surface. The 100%/100% figures above measure that overlap, not real-world
   distribution.
3. **Sample size**: 20 sites, 66 patterns, 350 instances. Two of the ten in-scope
   classes (`html-lang`, `document-title` — the two FULL-coverage criteria) had **zero**
   violations found on any of the 20 sites, so this study says nothing about their
   real-world frequency either way (professional sites rarely omit title/lang; that is
   itself a real and plausible finding, just an N=0-instances one).
4. **Same-provenance bias** (critic.md, verbatim): Beacon and Lighthouse both wrap
   axe-core-style rulesets; "two of three judges agree" is partially the same
   detection logic counted twice, not fully independent triangulation.
5. **Correlated blind spot** (critic.md): anything requiring rendered state,
   interaction, or human judgment (reading order, color-alone meaning, post-submit
   errors, name-*correctness*) is invisible to all three judges in this study, not
   just to Beacon — so this population cannot even in principle speak to those
   criteria's real-world volume.
6. **Not computed**: a wider raw-Lighthouse pass over the 87/100-site benchmark
   (`beacon-benchmark-100/raw/*-lh.json`) would raise N and rule variety, but inherits
   limit 4 unchanged and does not resolve limit 2. Left as a disclosed future option,
   not built here.

## Is this publishable?

**Not as "X% of real-world accessibility problems fall inside Beacon's covered
criteria."** The 100%/100% figures are a correct read of this population but the
population's own scope was drawn to overlap with automatable/structural criteria
before Beacon ever entered the picture — publishing 100% invites exactly the
overclaim the "missing middle" framing is trying to avoid, just from a different
mechanism than the naive trap.

**What IS defensible, narrower framing** (if the team lead wants a citable number at
all): "In the 20-site ground-truth study measuring the 10 violation classes verifiable
independently of axe, every verified violation (66 patterns / 350 instances) fell
within Beacon's covered criteria (1.1.1, 1.3.1, 1.4.4, 3.3.2, 4.1.2)." That is a true,
narrow, re-derivable claim about a specific study — it is not a claim about "the
missing middle" of real-world accessibility problems in general, and should not be
worded to sound like one.

No number in this document should be read as strengthening the 25.5% headline; it
neither confirms nor refutes the "problems concentrate in a few criteria" hypothesis
the work order was testing for, because the dataset was never shaped to test that
hypothesis in the first place.
