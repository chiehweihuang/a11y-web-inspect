## Addendum (2026-07-25, hakuso HIGH fix + recalibration)

hakuso's first-pass audit (`plans/2026-07-25-ws-b-hakuso-audit.md`) found one HIGH:
`extractSameFileStyleRules`'s rule regex matched only the trailing `[.#][\w-]+` token
before `{`, so a compound (`.a.b`), descendant (`.parent .child`), or element-qualified
(`div.c4`) selector was mis-recorded under its bare tail token, resolving on any element
carrying just that one class — the exact false-certainty class this feature exists to
prevent.

- **Fix**: capture the full selector prelude before `{`, split on `,`, and only record
  entries matching the WHOLE string `^[.#][\w-]+$`. Rejected selectors are simply never
  recorded (unresolved by omission, same treatment as an external/unknown class).
- **Regression tests added** (6 new, `test/static-contrast.test.mjs`): all three leak
  shapes from the audit (compound, descendant, element-qualified — each on a
  partial-class element, asserting zero resolution), a control proving a compound
  selector never resolves even on a full-class element (rejected outright, not
  "moved" to a safer match), a control proving genuinely bare selectors still resolve,
  and a comma-separated-selector positive case (`.a, .b` each resolve independently).
- **Recalibration** (full detail in `plans/2026-07-25-ws-b-contrast-calibration.md`,
  current numbers at the top): resolved pairs 41 → **22** (21 → **9** sites), sub-threshold
  16 → **4**. This large drop is NOT new caution — it is the fix correctly removing
  resolutions that were already wrong. Tracing it by hand surfaced an important
  correction: **12 of the 14 OneTrust/TrustArc sub-threshold findings I had personally
  "verified" in the first calibration pass were themselves built on this exact bug** — my
  verification method (grepping for a substring like `#onetrust-pc-btn-handler {`)
  confirmed the token appeared before a `{`, not that it was the WHOLE selector; the real
  rule was `#onetrust-banner-sdk #onetrust-pc-btn-handler { ... }`, a descendant selector.
  One pair was also genuinely GAINED (a comma-separated selector list the old regex could
  only ever match the last entry of, dropping the other three legitimate independent
  selectors) — verified correct independently.
- **9 sites is below the original ≥10-site calibration bar.** Flagging explicitly rather
  than padding the sample to hit a number — the population itself shrank because several
  of the "sites" only had contrast findings via the now-rejected descendant-selector
  false certainties.
- Re-verified: bare `node --test` = **375/375 green** (18 baseline WS-B tests + 6 new).
  `node build.mjs --check` clean. Golden vectors regenerated again: still fingerprint-only
  diff, no finding changes. Score-neutrality spot-check re-confirmed on a real snapshot
  with new findings present (contrast category stays `not-machine-checkable`, `fail:0`,
  `overall_score`/`coverage_percent` unaffected).

## Design (resolvability boundary)

Per the dispatch's explicit conservatism spec: a pair only counts if EVERY step is
certain —
- **Foreground**: literal, opaque (alpha=1) color on the text-bearing element itself —
  inline `style`, or a SINGLE same-file `<style>` rule matched by exactly one of its
  classes (or its id, which always wins over class per fixed CSS specificity — a
  deterministic rule, not a guess) with no conflicting redeclaration anywhere in the file.
- **Background**: same certainty bar, checked on the element itself first, then walked up
  through direct ancestors (tag-stack walk, mirrors `computeHiddenRanges`'s approach —
  this file has no real DOM). Stops (unresolved) at the first ancestor whose own
  background is declared-but-uncertain (gradient/`url()`/`var()`/alpha<1/class tie) — see
  the calibration-driven fix below for the biggest addition to what counts as
  "uncertain". Reaching the document root with nothing declared anywhere is ALSO
  unresolved — deliberately NOT defaulting to the white canvas the way tier-2's real
  browser safely does, because static analysis of one file cannot know whether some
  external stylesheet sets `body`'s background.
- No external CSS (`<link>`) is ever consulted, at any point.
- Uniform 4.5:1 threshold only (matches the plan's own evidence-line wording,
  「可靜態解析的 N 組配對中，M 組低於 4.5:1」) — no static large-text (18pt/14pt-bold)
  carve-out; that would need the same certain-literal treatment for font-size/weight and
  wasn't asked for here.

## A real bug found and fixed via FP calibration (see the calibration file for full detail)

Pre-fix, the detector resolved 196 pairs across 26 benchmark sites. Manual adjudication
caught a genuine false-certainty on snapshot 92: an icon `<span class="... bg-white ..."
style="color:#06C755">` had its real (external, Tailwind-utility-class) white background
silently skipped past, and the walk picked up an unrelated ancestor's inline GREEN
background instead — a false 1.00:1 ratio (green-on-green, a dead giveaway). Root cause:
"no matching same-file rule for this class" was being treated as proof nothing sets that
property, which is only true if you assume the only stylesheet in existence is the
same-file one.

**Fix**: an element carrying ANY class that doesn't resolve to a certain background via a
same-file rule now blocks that level of the ancestor walk, the same as an
ambiguous/gradient/image background — it does not get silently skipped. This is strictly
MORE conservative (can only turn a resolved pair into an unresolved one). Cost: resolved
pairs 196 → 41 (79% fewer), sites 26 → 21, sub-threshold findings 17 → 16 (only 1 of the
original 17 depended on the unsafe path — the rest resolve directly on the flagged element
itself via inline or an id/class rule, untouched by the fix). Regression test added
reproducing the exact pattern.

I nearly flagged a SECOND case as suspicious (site 91, a CSS-in-JS component with ~80
opaque hashed classes and an inline `style` containing only CSS custom properties, no
literal color) — traced it by hand and confirmed it's CORRECT: two of those hashed
classes are each declared exactly once in the file's own `<style>` block with the exact
fg/bg the detector reported (a vanilla-extract-style build that emits one atomic class per
property, inlined for SSR). Recorded in the calibration file as a "looked scary, checked
out" example, not a false positive.

## Risks / flags

- The 79% drop in resolving power from the calibration fix is real and intentional —
  flagging in case the team wants to revisit the class-blocking rule's strictness once
  more real-world data exists (e.g. a softer rule for classes that appear SOMEWHERE in the
  file's `<style>` blocks for OTHER properties, just not this one — I deliberately did NOT
  build that nuance, ship-the-lazy-version-and-flag-it).
- FP calibration here is a single benchmark run with hand-adjudication of the full
  post-fix population (41 pairs), not an exhaustive re-derivation of every row nor a
